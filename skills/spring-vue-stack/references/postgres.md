# PostgreSQL 数据参考

用于数据模型、SQL、索引、约束和迁移任务。先检查 PostgreSQL 主版本、Schema 组织、ORM/SQL 层、迁移工具和已发布的数据库契约。

## 建模与约束

- 遵循现有命名、主键、审计字段、软删除、版本列和 Schema 约定；不要自行引入新的全局模板。
- 新表和列使用项目统一、可移植且易读的命名，通常采用小写 snake_case，避免需要双引号才能区分大小写的标识符及容易与 SQL 关键字冲突的名称。不要仅为套用其他数据库手册而改变 PostgreSQL 类型、布尔值、主键或默认值的既有设计。
- 让数据约束表达稳定的不变量：根据语义考虑 `NOT NULL`、`UNIQUE`、`CHECK`、外键以及默认值。若约束有意放在应用层，说明一致性边界。
- 选择与数据语义相符的类型、精度、时区和空值策略。评估 JSON/JSONB 是否保留了确有价值的灵活性，避免把有稳定关系的字段无理由藏入文档列。
- 金额、比例和需要精确十进制语义的值使用适当的精确数值类型及明确精度/舍入规则，不用 `real`/`double precision` 承担金额相等判断。日期时间字段区分日期、本地时间和时间点，明确时区解释。
- 使用 JSONB 时，先确认 ORM/JDBC 驱动对目标 Java 类型的实际映射能力；需要自定义 TypeHandler、Converter 或序列化器时集中实现并复用，明确 SQL 类型为 `jsonb`、空值语义和反序列化错误处理。避免每个 Entity/Mapper 各自手写不一致的 JSON 字符串转换；通过集成测试覆盖写入读取、空值和格式错误等行为。
- 索引应服务真实查询、连接、排序或唯一性需求。索引会增加写入和存储成本；检查谓词、列顺序、选择性和现有索引后再添加。
- PostgreSQL 的具体功能、DDL 选项和锁行为会受服务器版本影响；版本敏感的决定先查目标版本文档。

## 迁移与运行风险

- 使用项目既定迁移工具和版本策略，不以手工改库替代迁移记录，也不擅自重写已在其他环境运行的迁移。
- 评估旧应用与新 Schema 的兼容窗口。高风险变更可拆成扩展、回填、切换、收缩等阶段。
- 对大表重写、长事务、索引构建、默认值回填和锁定风险，估算数据规模与执行时间；需要时选择并发/分批方案并核对该版本的限制。
- 数据回填应可重入、有边界并可观察。删除列、收紧约束或不可逆转换前，确认旧数据处理、备份和恢复方案。
- 不在未获授权的情况下对非隔离数据库执行迁移、导入、清理或破坏性 SQL。

## 查询与事务

- 只选择必要字段，避免无界读取和不必要的 `SELECT *`；使用参数绑定，动态表名、列名和排序语法需由允许列表构造。
- 检查分页排序是否稳定、过滤/连接/排序是否能利用合适索引、返回行数是否有界，以及事务是否过长。对大偏移分页评估游标/键集分页等适合当前访问模式的方案，不机械采用单一分页方式。
- 依据项目现有隔离级别和冲突处理方式处理并发；遇到死锁/序列化失败时，确认可安全重试的边界。
- 避免循环内逐条访问数据库造成 N+1；按业务边界考虑批量查询/写入，同时限制批次大小并保留事务和错误处理语义。ORM 使用时关注延迟加载、关联序列化和批量写入是否产生意外 SQL。
- 对关键查询先核对真实 SQL 和代表性数据分布，再评估执行计划；索引不是越多越好，查询改写也不能牺牲结果正确性。

## 文档同步

若新增/删除实体、修改字段、迁移或约束，按项目规则同步数据模型、迁移说明和 API 类型文档。数据库列名、表名前缀和字段顺序都以目标项目为准。
