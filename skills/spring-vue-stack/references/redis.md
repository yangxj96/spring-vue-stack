# Redis 状态与缓存参考

用于缓存、会话、限流、验证码、协调和其他 Redis 用法。先确认每类 Key 的用途、权威数据源、敏感度、过期语义、故障策略，以及项目对 Redis 部署和序列化的要求。

## 先区分数据角色

- **可丢失缓存**：源数据在其他系统中可恢复。确认未命中、过期或 Redis 故障时的回源行为、负载影响和允许的陈旧窗口。
- **安全状态**：Token、Session、一次性凭据、防重放或登录失败状态可能承担安全事实源职责。不能因为名字包含 `cache` 就按可丢失缓存处理；根据认证/授权契约明确故障时是否必须拒绝请求。
- **协调或队列状态**：锁、租约、工作队列和分布式限流有不同的原子性、续期及恢复要求。不要把通用缓存注解当作实现这些协议的替代品。

遇到连接超时、命令错误、脚本异常或结果不可判定时，不能擅自把错误解释为“Key 不存在”。先沿调用链查明状态语义，再按项目安全约定决定是否拒绝、重试或降级。

## Key、TTL 与序列化

- 使用可识别的命名空间，包含必要的应用/环境/领域信息；沿用项目命名约定，避免把类名或实现细节固化在外部 Key 契约中。
- Key 不应包含明文 Token、密码、验证码等秘密或不必要的个人信息。确需稳定关联时优先使用项目批准的不可逆标识。
- 为临时状态明确 TTL、刷新方式和过期后的行为。TTL 长短取决于业务有效期、数据变化频率与风险，不使用无依据的统一数值。
- 确认序列化格式、类型元数据、字符编码和升级兼容性；避免未经评估的语言/框架原生对象序列化。
- 设置容量与基数预期，防止高维参数、不受控输入或版本变化造成 Key 膨胀。

## 一致性、并发与失效

- 明确缓存失效时机和一致性窗口。写库成功后如何失效、消息延迟或并发刷新会产生何种短暂状态，都应符合业务允许范围。
- 检查热点 Key、缓存击穿、雪崩和穿透风险。使用随机过期、请求合并或回源限流前，先核对项目已有机制。
- 分布式锁或脚本操作需保证所有权校验、过期、释放与重试边界正确；跨多个 Key 的原子性依赖部署模式和 Redis 版本，应查证实际条件。
- 安全或业务关键状态的降级不能仅为保持可用性而放宽约束。将允许的故障行为记录在接口/运维说明中。

## Spring 集成

若项目使用 Spring Cache，先检查已有的 CacheManager、KeyGenerator、序列化和注解规则。缓存注解可能受代理、自调用和事务时序影响；在新增前确认失效和执行顺序。普通缓存建议与安全状态实现分开评估。
