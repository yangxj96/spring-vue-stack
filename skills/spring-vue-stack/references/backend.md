# Spring Boot 后端参考

用于服务端功能、API、验证、安全和持久化相关任务。

标准栈：Java 25 · Maven · Spring Boot 4.x · MyBatis-Plus · Flyway · PostgreSQL · Redis · Spring Security + Redis 存 UUID token（新项目可选 Sa-Token，二选一）· Lombok + MapStruct。完整约定见 [standard-stack.md](standard-stack.md)。先检查目标项目的依赖版本、模块边界和相邻功能实现；仓库显式声明了其它方案时以仓库为准，但不要因为示例来自历史项目就照搬其专有实现。版本敏感的行为以目标项目依赖版本对应的官方文档为准。

本文件覆盖核心规范、分层、DI、API 与序列化、时间、配置、并发语义与测试；数据访问见 [backend-persistence.md](backend-persistence.md)，认证/安全/文件/运行与线程见 [backend-security-ops.md](backend-security-ops.md)。

## 功能优先的分层约定

新功能按业务功能组织代码，使一个功能的 HTTP 入口、业务实现、数据访问和数据模型能够一起定位。包名和目录应反映业务能力，例如 `user`、`order`、`catalog`，不要把所有功能分别堆入全局 `controller`、`service`、`mapper` 包。

推荐的基础结构如下；按项目模块和实际职责调整包名，但保持同一功能的实现内聚：

```text
com.example.app
├── configuration
│   ├── WebConfig.java
│   └── PersistenceConfig.java
├── runtime
│   └── StartupInitializer.java
├── integration
│   └── notify
│       └── NotifyClient.java
├── properties
│   └── NotifyProperties.java
├── user
│   ├── controller
│   │   └── UserController.java
│   ├── service
│   │   ├── UserService.java
│   │   └── impl
│   │       └── UserServiceImpl.java
│   ├── mapper
│   │   └── UserMapper.java
│   └── javabean
│       ├── converter
│       │   └── UserConverter.java
│       ├── domain
│       │   └── UserSummary.java
│       ├── enums
│       │   └── UserStatus.java
│       ├── constant
│       │   └── UserConstants.java
│       ├── entity
│       │   └── UserEntity.java
│       ├── from
│       │   └── UserCreateFrom.java
│       ├── dto
│       │   └── UserDTO.java
│       ├── bo
│       │   └── UserBO.java
│       └── vo
│           └── UserVO.java
└── resources
    └── mapper
        └── user
            └── UserMapper.xml
```

各层职责：

- `controller`：HTTP 路由、协议边界、请求绑定和响应适配；只编排调用，不承载业务流程或 SQL。
- `service`：声明功能服务的业务操作契约，接口放在 `service`。统一继承 MyBatis-Plus 的 `IService<T>`（`XxxService extends IService<XxxEntity>`）；可按情况抽取统一的 `BaseService` 后再使用。项目显式采用其它 Service 组织方式时以项目为准。
- `service/impl`：实现业务规则、权限后的业务校验、事务边界和多个数据/外部服务调用的协调。实现类统一继承 MyBatis-Plus 的 `ServiceImpl<XxxMapper, XxxEntity>` 并实现对应 `XxxService`，需要时统一抽取 `BaseServiceImpl` 作为基类。业务规则不应散落在 Controller 或 Mapper 中；MyBatis-Plus 提供的通用方法可直接用，复杂业务写在自定义方法里。
- `mapper`：数据访问接口，统一继承 MyBatis-Plus 的 `BaseMapper<XxxEntity>`，从而获得通用 CRUD。每个 Mapper 接口都在 `resources/mapper` 下有同名 XML（即使当前没有自定义语句，也保持一一对应以便后续扩展）；保持文件名与接口名一致，XML 的 `namespace` 精确指向 Mapper 全限定类名，自定义语句 `id` 与接口方法名及参数/返回类型一致。复杂查询、多表连接和批量操作写在 XML，简单 CRUD 优先用 `BaseMapper`/条件构造器。新增或移动接口时同步移动 XML 并检查 Mapper 扫描、资源路径配置和构建产物中的 XML。
- `configuration`：集中放置通用 Spring 配置类和跨功能基础设施配置，例如 Web、序列化、持久化、线程池或客户端 Bean 配置。按职责拆分配置类，避免单个配置类成为杂项集合；功能专属配置是否放在功能包内，沿用项目既有约定。此目录存放 Java 配置代码，不存放环境密钥或实际配置值；配置值按“配置绑定与密钥”一节从外部注入。
- `runtime`：按需放置应用启动或生命周期阶段执行的任务，例如 `ApplicationRunner`、`CommandLineRunner`、启动数据校验、受控的初始化或生命周期协调逻辑。启动任务应有明确执行时机、失败策略和重复启动/多实例语义；不要把常规业务 API 流程、无边界数据修复或耗时阻塞任务藏在启动钩子中。Bean 的创建和基础参数绑定仍放在 `configuration`，实际业务规则委托给相应功能 Service。
- `integration`：按需放置对外部系统的适配层和客户端封装，例如邮件/通知、支付、对象存储，或对 OkHttp 等底层 HTTP 客户端的项目级封装。按外部系统或能力建立子包；封装统一处理协议细节、认证、超时、错误转换和可观测性，向功能 Service 暴露稳定且符合业务需要的接口。不要让第三方 SDK/HTTP 响应类型扩散到 Controller 或多个业务功能，也不要在这里重复实现业务规则。客户端 Bean 的装配与通用配置放在 `configuration`，调用场景及业务决策保留在功能 Service。
- `properties`：按需放置通过 Spring Boot 配置绑定创建的类型安全配置属性类。按配置前缀或职责组织，并校验必填项和取值范围；实际环境值仍从外部配置或 Secret 注入。若项目惯例将属性类放在 `configuration.properties` 或模块内部，沿用其布局。
- `javabean` 下可按需使用以下常见子目录。它们是预先约定的职责名称，不表示每个功能都必须建立全部目录；没有对应模型时不创建空目录，也不要为了填满结构而新增无用类型。
  - `converter`：功能内边界模型转换器，例如 From/DTO/Entity/VO 转换。可使用 MapStruct 或手写的明确转换；保持转换集中，避免多层重复转换。转换器不承载查询、权限或业务决策。
  - `domain`：具有明确业务语义的值对象、领域模型或 Mapper 专用查询结果模型。不要把它当作 `BO` 的别名；是否使用领域对象及其建模方式由项目架构决定。
  - `entity`：持久化模型，与表结构或 ORM 映射相关。按项目 ORM 约定使用；不要直接作为公开 API 响应。
  - `from`：功能入口接收的请求模型，包含新增、修改、操作以及列表查询的输入。查询条件、分页和排序参数默认也使用 From；动态排序字段须在数据访问边界按允许列表处理。只有目标项目已有明确的独立查询模型约定时，才另设 `query`。
  - `dto`：跨层、跨模块或外部服务之间传递的数据模型。仅在确有独立传输契约时使用；避免把 DTO 变成含义不清的万能对象，也避免与 From/VO 重复定义同一边界数据。
  - `bo`：承载业务处理中间数据或业务概念的对象，仅在其语义不同于 API 模型、Entity 和 DTO 时使用。不要因“Business Object”命名而把业务规则全部塞进数据对象。
  - `vo`：返回给调用方或上层的展示/响应模型。仅包含该输出契约需要的字段，不暴露密码、内部标记或持久化实现细节。
  - `enums`：功能内封闭值域的枚举及相关类型。若枚举跨功能共享，按项目共享模型约定放置，不复制多份。
  - `constant`：仅放具有稳定语义的功能常量。状态、类型和动作等封闭值域优先建模为枚举；不要用常量类维护可变配置或散落魔法字符串。
- 目录名、类名和模型边界优先沿用目标项目既有约定。不要把不属于某类职责的模型塞入对应目录；不要为同一份数据无理由串联 `From -> DTO -> BO -> Entity -> VO` 全套转换。模型转换放在清晰的边界或项目既有转换机制中，避免 Controller、Service 和 Mapper 各自重复转换。

`runtime` 和 `integration` 也是按需建立的通用顶层包，不要求每个项目都具备。若项目已有 `adapter`、`client`、`bootstrap` 等明确约定，优先沿用，并保持相同的职责边界，不要为同一职责并列复制多套目录。

按真实职责还可按需建立 `provider`（可替换的外部能力实现）、`sender`（消息或通知发送策略）、`dispatch`/`worker`（任务派发和后台处理）、`strategy`/`policy`（可替换策略或业务规则）、`validator`（可复用的领域校验）、`observability`（指标、健康检查等观测组件）和 `support`（有明确领域含义的跨子域协作组件）等包。不要把这些类型一律塞进 `service`，也不要创建没有实际职责的空包；纯无状态通用函数才适合工具包，避免形成职责不清的 `utils`/`common` 大杂烩。

## Java 与项目代码规范

- 标准栈为 Java 25 与 Maven；项目显式声明其它 JDK/构建工具时以项目为准。使用目标项目配置的语言级别、格式化器、静态检查和依赖管理方式；不要假定许可证头或构建命令。
- 依赖按项目统一的版本管理和模块边界声明；复用已有库前先检查其维护状态和现有能力，不重复引入功能相同的库，不提交未使用依赖或在多个模块声明冲突版本。引入第三方库时考虑兼容性、许可证、漏洞更新和构建影响。
- 遵循项目的许可证头、命名和注释约定；注释标准见 [comments.md](comments.md)（中文注释，L1/L2 必须）。新增公开类型、接口方法或复杂边界时写清用途、参数语义、返回值和失败条件；**实现类与覆写方法不重复接口 Javadoc**；不要虚构作者、版权信息或仓库没有采用的注释模板。
- Java 标识符使用清楚、一致的英文命名：类型使用 UpperCamelCase，方法、参数和字段使用 lowerCamelCase，常量使用语义完整的 UPPER_SNAKE_CASE；包名使用小写。避免拼音混写、难懂缩写、名称前后下划线或 `$`。测试类遵循项目约定，并能清楚对应被测单元。
- 覆写父类或接口方法时使用 `@Override`。限制类型和成员的可见范围；接口暴露稳定契约，不放实现细节。方法名表达行为，CRUD 查询、保存、更新、删除的命名在同一服务内保持一致。
- 业务内部受控且封闭的状态、类型、渠道和动作优先使用枚举或类型化表示。第三方开放状态码在集成边界解析；若其属于内部封闭状态，再转换为内部枚举，避免魔法字符串散布在业务代码。
- POJO 的字段命名需兼容项目使用的 JSON/ORM/Bean 访问约定；布尔属性优先用 `enabled`、`deleted` 等语义字段名，避免字段本身命名为 `isEnabled` 后在不同序列化器中产生属性名歧义。
- 按语义选择基本类型或包装类型：值必定存在时可用基本类型，需要表达“未提供/未知”时用可空类型并显式处理 null。金额和精确十进制计算使用 `BigDecimal` 等精确类型，不使用二进制浮点直接判断金额相等；包装数字比较值而非对象引用。
- `equals` 与 `hashCode` 必须成对且符合对象相等契约；作为 Set 元素或 Map 键的对象，其参与比较的状态在集合使用期间应保持稳定。不要对浮点数用直接相等比较表达业务精度。
- 条件和循环使用明确分支，避免 switch 意外贯穿；复杂条件拆成有意义的局部变量或小方法，深层嵌套优先用校验失败后的提前返回降低理解成本。重复使用的正则表达式在合适的作用域预编译，不在高频循环里反复编译。
- 在循环中构造大量字符串时使用 `StringBuilder` 等合适方式，避免每次迭代产生不必要的中间字符串；不为少量简单拼接做无测量的微优化。
- 注释解释业务原因、约束和不明显的决策（深度分级见 [comments.md](comments.md)），不重复翻译代码；修改逻辑时同步更新注释。删除废弃代码，不把长期注释掉的旧实现留在源码中；TODO/FIXME 应说明后续事项并按团队流程清理。
- 使用项目定义的持久化基类、审计填充、主键生成、软删除和版本控制机制（若存在）。不要在 Controller/Service 手工复制自动填充字段、主键生成或绕过乐观锁；新增实体时先确认基类和数据库迁移约定。
- 标准栈下 Service 继承 MyBatis-Plus `IService`/`ServiceImpl`，并可使用项目统一的 `BaseService`/`BaseServiceImpl` 或 Repository 基类、统一分页模型来叠加项目抽象；不要绕过项目抽象直接在 Controller 调用通用 ORM 接口，也不要同时维护两套并行基类。项目没有统一基类时，不为形式强加一层。
- 功能内 From、VO 等模型按现有后缀和验证风格命名。写入请求使用项目支持的 Bean Validation 分组或等效机制区分创建/更新规则；时间字段采用类型化时间模型和明确格式，不把未经约定的自由文本当作时间值。

## 代码生成与对象映射工具

Lombok 和 MapStruct 属于标准启用项。引入前仍检查目标项目的依赖、构建插件/注解处理器配置：项目显式关闭某项时遵循项目，不加装；项目已使用时按既有版本、配置和编码风格使用，不混用两套重复机制。

- **Lombok**：标准启用。沿用项目对 `@Getter`、`@Setter`、构造器及日志注解的范围约定；检查生成方法是否会影响实体访问、序列化、代理或框架反射。对可变性、相等性和哈希行为有业务含义的类，不要不加判断地用 `@Data` 生成全部方法；需要稳定 API 或清晰调试行为时，可显式声明关键方法。确认 IDE 与构建使用相同的注解处理配置。
- **MapStruct**：标准启用，用于明确的模型边界转换，例如 `From`/`DTO`/`BO`/`Entity`/`VO` 之间的转换。沿用现有 Mapper 接口位置、组件模型、命名和生成策略；映射新增字段时检查是否需要显式映射、忽略或转换，避免关键字段因默认同名映射而产生意外结果。复杂业务规则、权限决策和数据查询不放进映射器。确认注解处理器在项目构建中运行，并检查生成代码或通过现有测试验证关键映射。
- 引入或升级这些工具会影响依赖、编译期注解处理和构建配置；只有任务确有需要且项目允许时再提出，并按项目依赖管理与验证流程处理。

模块和包之间保持单向、可解释的依赖方向，避免循环依赖。跨功能调用优先通过被调用功能的公开 Service 契约，不直接依赖另一个功能的 Controller、Mapper、XML 或实现类。共享代码只有在稳定且确实被多个功能复用时再抽取。

## Spring Bean 与依赖注入

- 必需依赖优先使用构造器注入；字段注入会隐藏类的真实依赖，不作为新代码默认写法。
- 由 Spring 容器管理的 Controller、Service、Mapper 和配置组件，应沿用项目的注解扫描与 Bean 注册方式。不要在业务代码中 `new` 一个本应由容器管理的依赖，也不要使用静态全局 Bean 查找器绕过依赖关系。
- 仅在确需显式组装第三方对象、客户端或条件化 Bean 时增加 `@Configuration`/`@Bean`；避免重复注册或无必要的配置层。
- 不要假定注解本身会产生某种行为；检查组件扫描范围、条件配置和目标 Spring 版本。

```java
@Service
public class UserServiceImpl extends ServiceImpl<UserMapper, UserEntity> implements UserService {
    // baseMapper 由 MyBatis-Plus 注入；这里演示对其它协作者使用构造器注入
    private final NotifyClient notifyClient;

    public UserServiceImpl(NotifyClient notifyClient) {
        this.notifyClient = notifyClient;
    }
}
```

## Spring Boot 4 与出站调用

- 出站 HTTP 调用优先使用 Spring 的 `RestClient`（或声明式 `@HttpExchange` 接口），统一处理超时、错误映射与重试；不要让底层 HTTP 细节散落各处。
- 版本基线与 Boot 4 / Jackson 3 兼容注意见 [version-baseline.md](version-baseline.md)；AOT/native 场景按官方提示配置，不要把运行期反射的假设带进 native 构建。

## API 边界、验证与异常

- Controller 负责 HTTP 路由、参数绑定、调用 Service 和适配响应；不要在其中编排多步业务规则或直接调用 Mapper。端点优先遵循项目已发布的 API 契约；新接口采用项目统一的 REST 风格，不能以风格整理为由私自更改已有路径或语义。
- 将 URL 建模为资源及其关系，路径使用名词表达资源，避免把普通 CRUD 动作写成路径动词。使用 HTTP 方法表达操作：`GET` 查询，`POST` 创建或提交非幂等操作，`PUT` 完整替换，`PATCH` 局部修改，`DELETE` 删除。特殊业务动作若无法自然表达为资源变更，沿用项目已有动作端点约定并保持语义清晰。
- 路径、查询参数和请求体各司其职：资源标识和必要的层级关系放路径；筛选、分页、排序等放查询参数；复杂创建/更新数据放请求体。不要把敏感值放在 URL 中；避免无必要的深层资源嵌套。
- 路径大小写、复数形式、单词分隔符、API 版本前缀和尾部斜杠遵循项目统一规范。新端点保持一致，不在同一资源下混用命名风格。
- API 线上的入参和响应字段名统一使用 `snake_case`（下划线分隔单词）；包括 JSON 请求体、JSON 响应体，以及 GET 查询参数名。Java 字段、方法参数和内部属性继续使用小驼峰，例如 JSON/query 中的 `user_name` 对应 Java 属性 `userName`。优先通过项目统一的 JSON 序列化配置完成请求/响应字段映射，不要在每个 DTO 上重复配置，也不要因此改动数据库列名约定。
- GET 查询参数在客户端使用 `snake_case`，后端需通过统一的 Spring MVC 配置/参数绑定适配机制将参数名映射到 Java 小驼峰属性；例如 `?user_name=alice` 绑定到 `userName`。Spring MVC 不应被假定会自动完成这种名称转换。适配需同时覆盖项目实际使用的直接 `@RequestParam` 和查询 From/`@ModelAttribute` 绑定方式，保留同名多值参数（如数组/集合），并对转换后发生名称冲突的输入明确拒绝或按项目定义处理；不要只在 Controller 中对个别参数手工改名。
- JSON 命名策略和 GET 参数适配属于两套不同的绑定路径，应分别检查和验证：覆盖含下划线字段、空值、集合/重复参数、分页参数及名称冲突等情况。生成的 OpenAPI/接口文档和前端类型也应展示线上 `snake_case` 名称。
- 响应统一使用统一壳 `{code,message,data}`（Java 侧类型为 `R<T>`），`code` 恒等于本次 HTTP 状态码：查询/更新成功 `200`，新建成功 `201`，删除/无返回操作成功 `204`（空 body），参数/语义失败 `400`，未认证 `401`，无权限 `403`，不存在 `404`，状态冲突 `409`，服务端异常 `500`。错误一定有 body，成功可以无 body（仅 `204`）；不要用 HTTP 200 包装所有失败，也不要将内部异常文本直接作为错误响应。完整状态码表见 [standard-stack.md](standard-stack.md)。
- 列表接口采用有界分页或明确的结果上限；校验页码、页大小和筛选范围。分页响应固定为 `200` + `data` 为 MyBatis-Plus `Page`（`records`/`total`/`size`/`current`/`pages`），按全局 snake_case 序列化。排序字段、方向和可筛选字段必须由服务端允许列表控制；排序需要稳定的次序以避免翻页时遗漏或重复。优先复用项目统一分页模型，不让每个 Controller 自创不同格式。
- 明确方法的幂等性和重复提交语义。符合 HTTP 语义的安全/幂等方法不得产生意外副作用；创建、支付等可能重复执行的操作，按业务需要采用项目既有幂等键或去重约束。
- API 输入使用 From 或项目现有请求类型，输出使用 VO 或项目现有响应类型。不要未经审查直接将 ORM Entity 暴露给 API，也不要把 API 字段变化当成内部重构。
- Controller 方法声明具体响应类型；无业务响应时返回 `204`（`ResponseEntity<Void>` 或等价写法），不用 `Object` 或无类型 Map 隐藏 API 契约。查询条件较多时封装为 From/查询对象；路径标识用路径参数，避免为单个查询字段机械创建大量 DTO。
- 在服务端信任边界验证必填、长度、格式、范围、状态转换和对象权限。Bean Validation 注解要与 Controller 参数校验机制配套，并确认嵌套对象校验已启用。
- 每个端点都要明确认证与授权策略：检查资源级权限和适用的数据范围；确需公开的端点也应按项目约定显式声明为公开。若项目要求审计，沿用统一审计机制记录业务动作，不要在每个 Controller 中自行写审计存储。
- 对 API 路径、HTTP 方法、字段、含义、错误码、状态码或权限要求的变化，检查前端调用方、其他客户端和接口文档。
- 复用项目现有异常类型、全局异常处理和错误响应。对预期业务失败使用有语义的项目异常，不使用裸通用异常表达所有失败；保留内部诊断原因，但不向调用方泄露堆栈、SQL、凭据或内部实现。
- 对受控的封闭值域使用枚举或项目已有的类型化表示；第三方可能扩展的开放值在适配边界处理，不要错误地拒绝未知值。
- 统一异常处理使用 `@RestControllerAdvice`（或项目等价机制）：把业务异常映射到标准 HTTP 状态与统一响应壳；**必须包含一个兜底处理器**（如 `@ExceptionHandler(Exception.class)`）捕获未预期异常，对内记录完整日志（含 traceId），对外只返回 `500` 与安全、稳定的提示，绝不泄露堆栈、SQL、凭据或内部实现。

## 序列化与 JSON 契约

统一通过全局 Jackson 3 配置完成（Spring Boot 4 默认，包名 `tools.jackson`，核心类型 `JsonMapper`、定制器 `JsonMapperBuilderCustomizer`）；只有项目显式引入 Jackson 2 时才用 `ObjectMapper`/`Jackson2ObjectMapperBuilderCustomizer` 写法，不混用两套。不在单个 DTO/VO 上重复配置。完整契约见 [standard-stack.md](standard-stack.md)。

- **字段命名**：JSON 请求/响应使用 `snake_case`，Java 属性保持小驼峰（见 API 章节）。
- **Long / BigInteger 精度**：主键为 UUIDv7 字符串；任何 `Long`/`BigInteger` 超过 JS 安全整数（2^53-1）时必须序列化为字符串，避免前端 JS 精度丢失；这类字段一出现就应检查是否需要字符串化。
- **时间**：绝对时刻输出带偏移或 UTC，本地语义用 `LocalDate`/`LocalTime`；两类时间的选型与反模式见 [standard-stack.md](standard-stack.md) 的「时间语义与取舍」，格式集中配置。
- **null 与集合**：按需决定是否输出 `null` 字段（默认输出以保持契约稳定）；集合默认返回空数组而非 `null`，减少前端空判断。
- **枚举**：对外输出稳定的字符串（枚举名或约定码），不输出 ordinal；新增取值前评估前端与旧客户端兼容。
- **BigDecimal**：金额等精确值按约定格式输出，避免二进制浮点误差。
- **不要序列化实体**：API 一律用 VO；实体双向引用会死循环（`StackOverflowError`）并泄露内部字段。见 [pitfalls.md](pitfalls.md)。
- 修改任何序列化规则都会影响全部接口，应评估对已有客户端的影响并同步接口文档。

## 时间、日志与审计

- API 日期和时间字段使用清楚、稳定且在接口文档中声明的格式。对带时刻的数据明确时区/偏移语义；持久化和跨系统交换不要依赖服务器默认时区。用户本地时间应在明确的时区边界转换。
- **时间语义要区分**：绝对时刻用 `Instant`/`OffsetDateTime` + `timestamptz`；生日、每日时刻等本地语义用 `LocalDate`/`LocalTime` + `date`/`time`，不要一律存成瞬时。
- **不要在模型转换或序列化中读取安全上下文做时区换算**：需要用户时区时把它作为**显式参数**传入，或放到独立的展示层处理；否则未认证、异步、定时任务、系统间调用会得到不一致结果，还会引入循环依赖。按用户时区本地化后也必须带偏移（`OffsetDateTime`），不得返回无偏移的 `LocalDateTime`。
- 诊断日志用于排障，业务审计用于回答谁在何时对什么资源执行了什么操作；遵循项目的日志级别、关联 ID 和审计设施，不在业务代码中重复写审计记录。
- 日志只记录排障所需的最少信息。不得记录密码、访问令牌、完整认证头、密钥或未脱敏的敏感请求/回调正文；记录第三方错误时先筛除其响应中的敏感字段。
- 把用户输入或外部响应写入日志前清理换行与控制字符、限制长度，避免日志注入与伪造日志行。
- 不要捕获异常后静默忽略或只记录后返回成功。转换异常时保留 cause 和可诊断上下文，同时通过统一异常映射对外返回安全、稳定的错误结构。

写操作的关键业务节点可按项目日志规范记录结果摘要和资源标识；不要将完整请求对象直接序列化进日志。异常类别应表达可恢复/业务拒绝/依赖故障等语义，并交由统一异常处理映射，避免裸 `RuntimeException` 成为常规业务错误协议。

异常处理还应遵循以下规则：

- 不把异常用于正常分支判断；应先判断可预见的空值、范围或状态条件。
- 只在能够恢复、转换或补充上下文的边界捕获异常，优先捕获具体类型。不得空 catch、只打印后继续成功返回，或为方便捕获整个大段不相关逻辑。
- 使用 try-with-resources 管理流、连接等资源。不要在 `finally` 中 return 或抛出新异常覆盖原始异常；保证事务异常按项目回滚规则向事务边界传播。
- 不捕获 `NullPointerException` 等程序缺陷来替代输入校验。转换异常时保留原始 cause，避免同一异常在多个层重复打印堆栈。

## 集合与并发安全

- 使用集合时理解其可变性和视图语义：`subList`、`keySet`、`values` 等可能是原集合视图或不可变视图；不要在迭代期间无保护地修改底层集合，也不要假定返回集合总可写。
- 为 Map 键和 Set 元素定义稳定的相等与哈希语义；禁止以可变字段参与哈希后再修改对象。需要保留顺序时选用有序集合，不能依赖普通 HashMap/HashSet 的偶然迭代顺序。
- 并发代码明确共享状态、可见性、原子性和生命周期。并发容器只保障其文档承诺的单个操作，不自动保证多步“检查再修改”原子；使用原子操作、锁、数据库约束或事务实现业务不变量。
- 不共享非线程安全对象。线程池、调度器和并发队列应有明确容量、拒绝/背压及关闭策略；在线程复用环境使用 ThreadLocal 时要在请求/任务结束清理，防止数据串用和内存滞留。线程模型、`@Async`、连接池与虚拟线程见 [backend-security-ops.md](backend-security-ops.md)。
- 避免无证据的微优化。先控制数据库往返、批量处理和无界分配；性能敏感改动用真实负载或基准证据支撑，并保持结果语义正确。

## 配置绑定与密钥

- 先沿用项目已有配置前缀、配置文件、环境变量覆盖方式和 Secret 注入路径，不在代码中增加环境专属地址或凭据。
- 一组有关联、需要类型转换或校验的配置，优先评估使用 `@ConfigurationProperties` 建立有类型的配置对象；通过项目采用的 Jakarta Validation 方式校验必填值和范围，并在配置错误时尽早失败。
- 少量单一配置可沿用项目已有的 `@Value` 等写法；不要为所有配置机械地套同一模式。
- 密码、Token、连接凭据不得写入源码、提交的示例配置、日志、异常消息或测试快照。日志输出配置对象时确认不会泄露敏感字段。

## 测试与验证

- 单元测试聚焦 Service 业务分支、边界条件和异常语义；Controller 测试验证路由、绑定、校验和响应契约；Mapper/数据库集成测试验证 SQL、映射、事务和真实数据库行为。按项目现有测试分层选择，不为满足模板而重复测试同一实现细节。
- 对新增业务逻辑覆盖正常路径、边界输入、失败路径和权限拒绝；对回归缺陷添加能稳定复现原问题的测试。每个测试只验证明确行为，命名清楚，不依赖执行顺序、当前时间、外部网络或共享开发环境状态。
- Mock 只替代测试边界上的外部依赖，不要把被测对象内部每个调用都 Mock 掉；重要 SQL、序列化、事务、Spring 代理和安全配置用项目适用的集成测试验证。
- 测试数据应隔离、可重复创建和清理；避免依赖真实生产凭据或把本地绝对路径写入测试。新增测试沿用项目测试框架、fixture 和命名约定。
- 新增 Mapper XML 时至少确认它参与资源打包，并通过项目既有 Mapper 或集成测试覆盖关键映射；单纯 Java 编译不一定能发现 XML 未加载或语句 ID 不匹配。
- 识别项目已有测试与质量门禁，选择与改动范围匹配的验证方式。命令以目标项目脚本为准（标准栈为 Maven）；不要把某项目的 Wrapper、插件或命令当成标准栈的一部分。
- 新增或修改公开接口时，同时检查调用方契约、授权路径和相关文档；数据库结构变更按 [postgres.md](postgres.md) 的迁移约定处理。
