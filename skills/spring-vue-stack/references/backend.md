# Spring Boot 后端参考

用于服务端功能、API、事务、验证和安全相关任务。先检查项目使用的 Spring Boot、Java 与数据访问依赖版本，再遵循仓库既有架构。

## 结构与边界

- 沿用现有模块和分层。新增代码应放在责任相符的位置；不要仅因熟悉某种架构就增加 Controller、Service、Repository 等平行层。
- HTTP 入口负责协议和请求边界；领域或应用行为放在项目中负责该行为的组件内。简单功能不必为了形式增加抽象。
- 跨模块调用优先通过已有公开接口、Facade、端口或事件。避免依赖其他模块的内部持久化模型和实现细节。
- 沿用项目选择的 ORM、SQL 映射、对象转换和 API 结果结构，不自动引入新框架。

## 输入、结果与异常

- 在信任边界验证输入，包括必填、长度、格式、范围、状态转换和对象权限；前端校验不能取代服务端验证。
- 使用具体、稳定且符合项目契约的请求和响应类型。对公开 API 的字段、语义或状态码变更，检查所有客户端及文档。
- 复用现有异常映射和错误响应机制。异常应保留足够的内部诊断信息，同时避免向调用者泄露堆栈、凭据或内部实现。
- 对受控的封闭值域，可使用枚举或项目已有的类型化表示；开放的第三方值应在适配边界集中解释，不要错误地限制未知供应商值。

## 事务与数据访问

- 先确认事务边界和现有一致性要求，再把事务放在能完整表达业务操作的层级。
- 检查事务中的外部调用、长时间操作、重试和副作用；需要时采用项目既有的 outbox、幂等或补偿方案。
- SQL、Repository 和 ORM 查询应满足真实访问条件。避免无界读取、未审查的动态排序/过滤和逐条查询造成的 N+1。
- 只有当共享行为的语义和依赖边界稳定时才抽取复用；避免过早引入通用框架或职责混杂的工具类。

## 安全与配置

- 对每个操作分别检查身份认证、资源级授权、租户/数据范围和输入可信度。UI 隐藏功能不构成授权。
- 使用参数绑定处理 SQL 值；对动态列名、排序方向和其他 SQL 结构使用允许列表。
- 密钥、密码、Token 和连接凭据通过项目批准的 Secret 或环境配置路径注入，不写入源码、日志、示例或错误消息。
- 区分普通性能缓存和安全/业务状态；外部依赖故障时的允许行为应由状态语义和安全要求决定，详见 [redis.md](redis.md)。

## 验证

识别项目已有测试与质量门禁，并选择与改动范围匹配的验证方式。不要把某项目的 Maven Wrapper、插件、命令或 JDK 版本当成通用要求。新增或修改公开接口时，同时考虑调用方契约及相关文档。
